# E1 — Findings store and an independent verifier (`exploit_verified` or it is not a finding)

Epic: **E05** · Lane: **E** · Depends on: nothing

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

Shannon: 'no exploit, no report' — only findings with status `exploited` reach the report and the CI gate. Xalgorix: a separate verifier re-exploits every candidate; inconclusive ones are flagged, never confirmed; labels 'Exploit-verified' vs 'Source-verified'. Buggy checks that cited captures exist and replay, but nothing re-proves the claim itself.

## Idea

A finding is a claim plus machine-checkable assertions. A verifier that did not make the claim re-sends the requests and evaluates the assertions. Only a pass makes it `exploit_verified`.

## Architecture

New package `buggy/findings/` (stdlib + `buggy.capture` + `buggy_core` only):
- `model.py`: `Finding` dataclass exactly per `board/CONTRACTS.md`; `finding_id(engagement, cls, endpoint, parameter)` (normalise endpoint: lower-case host, strip query, replace numeric/UUID path segments with `{id}`); `validate(dict) -> Finding` with field-level errors; enums for status/severity/class (class list imported from `benchmark.lab.taxonomy` is NOT allowed in product code — copy the 14 class names into `model.py` and add a test in `tests/unit/benchmark` that the two lists are equal).
- `store.py`: `FindingStore(path)` (SQLite, rollback journal). Tables `findings` (one row per id; JSON columns for assertions/verification), `finding_events` (append-only: id, at, actor, event, detail). Methods: `upsert(finding, actor)`, `get(engagement, id)`, `list(engagement, *, status=None, grade=None)`, `set_status(...)`, `events(engagement, id)`. A status can never go from `discarded`/`exploit_verified` back to `candidate` (raise).
- `verifier.py`: `verify(finding, gateway, *, sessions=None) -> Verification`. For each assertion: re-send the cited capture's request fresh through `gateway.send(..., replay_of=capture_id, note="verifier")` (with `identity` when the assertion names one and `sessions` is given); evaluate `expect` on the NEW response: `status` (int or list), `body_contains` (all), `body_not_contains` (none), `same_as: <capture_id>` (similarity >= 0.95 to that capture's response), `differs_from: <capture_id>` (similarity < 0.80 or different status). State-changing requests are re-sent only if `allow_state_change=True` is passed; otherwise the assertion is `not_replayed`.
  Outcome rules: every assertion passes -> `exploit_verified`; any assertion fails on a re-send -> `inconclusive` with the reason (NOT discarded: the target may be flaky); a cited capture is missing, out of scope, or from another engagement -> `discarded`; zero assertions -> `inconclusive: no assertions`; all assertions `not_replayed` -> `inconclusive: needs operator-approved replay`. A finding whose `source` starts with `source:` and has no assertions may be set `source_verified` only by an explicit call `mark_source_verified(finding, note)`.
  The verifier never trusts text supplied with the finding (title, description, evidence prose) for its decision.
- `service.py`: `FindingService(store, gateway, sessions=None)`: `submit(engagement, data, actor) -> dict` (validate, compute id, dedupe by id -> merge assertions, status `candidate`), `verify(engagement, id, *, allow_state_change=False) -> dict`, `get`, `list`. Returns JSON-serialisable dicts.

## Tests that must exist and pass

Using the `Site` fake origin and a real `CaptureGateway`:
- an IDOR-shaped finding (owner capture + attacker capture, `same_as` + `body_contains`) on a vulnerable fake -> `exploit_verified`, with new replay capture ids recorded.
- the same finding after the fake is "fixed" (attacker now gets 403) -> `inconclusive` with the failing assertion named.
- prose says "confirmed admin access" but assertions fail -> not verified (the text is ignored).
- missing capture id / capture from another engagement / capture whose host left the scope -> `discarded`.
- POST assertion without `allow_state_change` -> `inconclusive: needs operator-approved replay`, and no request was sent (assert the fake saw nothing).
- no assertions -> `inconclusive`.
- id stability: `/api/orders/1001` and `/api/orders/1002` same class+param -> same id; different parameter -> different id.
- illegal status transition raises; events are append-only and record actor.
- validation errors name the field.
