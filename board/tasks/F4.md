# F4 — Tool and domain readiness matrix: know what actually works before a run

Epic: **E10** · Lane: **F** · Depends on: F3

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

HexStrike exposes `/health` with tool availability; CyberStrikeAI skips or substitutes missing tools at runtime. Buggy inherits a wide specialist roster (AD, cloud, C2, reversing, mobile, wireless...) whose tools and services nobody has checked on this build; breadth that is not verified is a claim, not a capability.

## Idea

Check every declared tool inside the sandbox and report, per specialist domain, whether it can run in the current stack.

## Architecture

New `buggy/readiness.py` + `cli/tools.py` (read `packages/buggy-core/buggy_core/capabilities.py` first: it declares every capability with its binary, delivery and lifecycle).
- `binaries() -> list[ToolSpec(name, binary, capability, domains)]` derived from the capability registry (no second list).
- `probe_script(specs) -> str`: one POSIX shell script that prints one JSON line per tool: `{"binary": ..., "found": bool, "path": ..., "version": first line of `<bin> --version|-V|version` (timeout 5 s each), "error": ...}`. It only runs version/help flags; it never runs a tool against a target.
- `check(execute: Callable[[str], str], specs) -> list[ToolStatus]` where `execute` runs a command in the sandbox (production: the sandbox backend's `execute`; tests: a fake).
- Domain map: for each agent role (read `packages/buggy/buggy/graph_registry.py` and `capabilities.role_capability_policy`) the required tools and required compose services/profiles (e.g. `ad` needs the `ad` profile services). `domain_readiness(tool_status, running_services) -> list[{domain, ready: bool, missing_tools, missing_services, note}]`.
- CLI: `buggy-cli tools check [--json] [--domain NAME]` prints the matrix; exit 0 always unless `--require DOMAIN` is given and that domain is not ready (exit 4). Output states plainly "ready", "degraded (missing: ...)", "not available in this stack (needs profile X)".
- `docs/readiness.md`: how to read it; the matrix from this repo's Kali image is added by the integrator after a real run (leave a marked placeholder section, do not invent results).

## Out of scope

Installing tools. Running any tool beyond a version/help flag. Editing the capability registry.

## Tests that must exist and pass

- the tool list is derived from the registry (adding a fake capability in a test shows up in the matrix).
- probe script output parsing: found with version, found without a version flag, missing, timeout.
- domain readiness: all tools present + services running -> ready; a missing tool -> degraded and named; a missing service -> not available with the profile named.
- the script contains no target-facing invocation: assert every command line ends in a version/help flag (parse the generated script).
- CLI `--json` shape and `--require` exit code.

## Done when

Tests pass.
