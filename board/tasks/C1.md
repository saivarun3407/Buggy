# C1 — SQL injection probe (boolean, error and time based, with controls)

Epic: **E09** · Lane: **C** · Depends on: nothing

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

Xalgorix and Strix list SQLi as a core class and bundle sqlmap; Shannon has a dedicated Injection agent and only reports what it exploited. Buggy's lab baseline covers 0 of 6 injection bugs deterministically.

## Idea

A small, bounded probe that confirms SQL injection in one named parameter by differential behaviour, not by pattern-matching a scanner's output.

## Architecture

Follow the existing pattern exactly: a function `name(ctx: Context, params: dict) -> ProbeResult` in a new module under `capture/probes/`, registered with a `ProbeSpec` in `capture/probes/registry.py` (add your entries at the end of the tuple; import your module at the top). All requests go through `ctx.send`. Verdict rules that apply to every probe:
- `vulnerable=True` only with a control that rules out coincidence (stated per probe below).
- `vulnerable=None` ("could not tell") when the baseline request fails, the gateway refuses, or signals conflict. Never guess.
- `evidence` lists the capture ids of baseline, control and proof requests; `details` names which is which.
- `remediation` is specific to the class.
- Payload lists are short and fixed (constants in the module). No destructive payloads: nothing that writes, deletes, sleeps longer than the stated bound, or reads files other than the stated markers.

Module `capture/probes/injection.py`, probe name `sqli`, class `injection`, CWE-89, `state_changing=False` when `method` is GET, else True.
Params: `url`, `method` (default GET), `parameter` (name), `location` (`query|json|form`, default query), `value` (a valid baseline value), `body` (for json/form), `headers`.
Algorithm (max 9 requests):
1. Baseline B with the valid value, twice. If the two differ by more than `similarity < 0.98` -> the page is unstable -> `None`.
2. Boolean pair: TRUE = `value' AND '1'='1` and FALSE = `value' AND '1'='2` (and the numeric variants ` AND 1=1` / ` AND 1=2` when `value` is numeric). Vulnerable-by-boolean when TRUE is similar to B (>= 0.95) and FALSE is clearly different (< 0.80 or different status) — for either variant.
3. Error signal: `value'` (single quote). Match the response against a fixed list of DBMS error signatures (SQLite, MySQL, PostgreSQL, MSSQL, Oracle: at least 3 patterns each). An error signature alone gives `vulnerable=True` only if the quoted-pair control `value''` (two quotes) does NOT show the signature.
4. Time signal, only if 2 and 3 are negative and `allow_time=true`: one request with a 3-second delay payload per DBMS family (max 3 requests, e.g. `' AND 3=(SELECT 3 FROM pg_sleep(3))--`), vulnerable when elapsed >= baseline + 2.5 s AND a matching zero-delay control stays within baseline + 1 s.
`details`: `technique` (`boolean|error|time`), `dbms_guess`, the payloads used, similarity numbers.
Remediation text: parameterised queries; do not build SQL from request data.
