# D5 — Tool-call guard: ordered rules over every argument, decoded, before execution

Epic: **E03** · Lane: **D** · Depends on: D4

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

CyberStrikeAI's tool guard runs immediately before execution, independently of approvals: ordered regex rules over the tool name and the serialized arguments, including nested strings and up to three rounds of percent-decoding, with a separate 'blocked' status and a dry-run. Buggy's `forbidden_command_patterns` only sees the raw `command` string of shell tools.

## Idea

Extend the existing forbidden-pattern mechanism to every gated tool and every argument, with decoding, without weakening anything that exists.

## Architecture

1. New `packages/buggy-core/buggy_core/types/tool_guard.py`:
   - `flatten(args) -> list[str]`: every string in the (nested) argument structure, plus dict keys, plus the compact JSON serialization.
   - `decode_rounds(text, rounds=3) -> list[str]`: the text and each successive `urllib.parse.unquote_plus` result while it keeps changing (max 3), plus one pass of HTML-entity and `\xNN`/`\uNNNN` unescaping.
   - `GuardRule(pattern, name="", tools=("*",), message="")`; `compile_rules(patterns_or_dicts)` accepts the existing plain regex strings (meaning: all tools) and dicts `{pattern, name, tools, message}`; invalid regex -> the rule is rejected with an error list (never silently skipped); cap 100 rules, pattern length 4096.
   - `evaluate_call(tool_name, args, rules) -> GuardDecision(blocked: bool, rule: str, match: str, where: str)`: first matching rule wins; checks tool name and every flattened + decoded string; uses `re` with a per-rule time budget guard (patterns are operator-authored; still, cap input length per string at 100k).
2. `packages/buggy/buggy/middleware/roe.py`: in `_evaluate`, for every gated tool (not only shell tools), after the existing checks pass, run `evaluate_call` with rules compiled from `rules.forbidden_command_patterns` plus a new optional `machine_enforcement.tool_guard` list. A hit is a refusal with code `TOOL_GUARD_BLOCKED` (message names the rule, not the full pattern) and is written to the ledger with `event: tool_guard_blocked`. The existing `evaluate_command` behaviour for shell commands is unchanged (keep its tests passing).
3. `MachineEnforcement.from_dict`: parse `tool_guard` (list) into a new tuple field; `parse_roe_document` rejects invalid rules with `InvalidRoEError`.
4. `cli/scope.py`: new subcommand `scope test-call <engagement> --tool NAME --args JSON` — dry-run, prints whether it would be blocked and by which rule; exit 0 allowed / 1 blocked. Add it without touching the other subcommands' behaviour.

## Files you own

## Out of scope

Changing approvals, the egress guard, or the capture gateway. A UI.

## Tests that must exist and pass

- a rule `(?i)drop\s+table` blocks `http_send` whose JSON body contains `DROP%20TABLE`, `DROP%2520TABLE` (double-encoded) and `DROP&#32;TABLE`; does not block `dropdown table` (negative control).
- nested argument structures and dict keys are inspected.
- per-tool rules apply only to the named tools.
- invalid regex in the scope file -> the scope is rejected at load (not ignored).
- a blocked call is not executed, is ledgered as `tool_guard_blocked`, and the refusal text does not leak the full pattern.
- `scope test-call` exit codes and output.
- every existing test in `tests/unit/middleware/test_roe*.py` and `tests/unit/hardening` still passes.

## Done when

RoE, hardening and core suites green.
