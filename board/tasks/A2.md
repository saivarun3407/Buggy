# A2 — `buggy-cli status <engagement>`: one snapshot of a run, with `--json` and `--follow`

Epic: **E01** · Lane: **A** · Depends on: nothing

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

Shannon exposes `status --json` and per-agent logs; PentAGI and RedAmon show live phase and tool activity. Buggy shows recon progress only while `hunt` is attached.

## Idea

A read-only command that assembles everything known about an engagement from the stores it can reach and prints it. It is also the data source for the dashboard page (task A6) and for `hunt` resume (A5).

## Architecture

New module `cli/status.py` with a pure core:

`snapshot(engagement, *, control: Path, audit: Path, fetch: Callable[[str, str, dict], dict], now: float) -> dict`

`fetch(server, tool, args)` is `buggy.tools.stack_mcp.call_mcp_sync` in production and a fake in tests. Every remote read is wrapped: an error or a missing tool becomes `{"available": false, "detail": ...}` for that section, never an exception.

Returned sections:
- `scope`: mode, in/out scope, rate limit, sandbox_egress, approvals setting (from `control/<e>/roe.json`), `program` (platform/handle if `program.json` exists).
- `recon`: from `recon_summary`: `state` (`not_started | running | completed | failed | interrupted`), `stage`, `stages_done`, `started_at`, `elapsed_s`, `records` by type, `scope_drops`.
- `approvals`: counts `pending / allowed / denied` and the pending list (`request_id, tool_name, reason, method+url` when present), from `audit/<e>/approvals/requests.jsonl` joined with `control/<e>/approvals/decisions.jsonl`.
- `evidence`: capture count and last capture time (`http_captures` with `limit=1` plus its `count`).
- `findings`: counts by `status` and by `grade`, and the list of `exploit_verified` (`id, title, severity, class`), from `findings_list` (may be unavailable until integration).
- `agents`: last ledger line of `audit/<e>/roe-decisions.jsonl` (time, tool, decision) and counts of allow/refuse.
- `next`: a list of plain-language next actions computed from the above (e.g. "2 requests wait for approval: buggy-cli approvals list acme").

CLI: `buggy-cli status <engagement> [--json] [--follow [--interval 5]] [--control-root] [--audit-root]`. Human output: compact sections, at most ~25 lines. `--follow` reprints when the JSON changes, until Ctrl-C or until recon is finished and nothing is pending.

## Files you own

## Out of scope

Writing anything. Editing `hunt.py`, `stack_mcp.py`, the web app.

## Tests that must exist and pass

- full snapshot from fixture files and a fake `fetch`; assert every section and the `next` hints.
- recon states: no run, running with stage, completed, interrupted.
- approvals join: pending vs decided; a denied request is not pending.
- each remote section degrades to `available: false` when `fetch` raises or returns `{"error": ...}`, and the command still exits 0.
- unknown engagement (no control dir) -> exit 2 with a clear message.
- `--json` output parses; `--follow` stops by itself when done (inject the sleep and a sequence of snapshots).

## Done when

`buggy-cli status <e> --json` returns a truthful snapshot for an engagement directory created in a test.
