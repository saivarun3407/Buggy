# A6 — Dashboard: engagement run page (recon, approvals, evidence, findings)

Epic: **E12** · Lane: **A** · Depends on: A2

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

PentAGI and RedAmon show a run live: phase, activity, findings, with approve/deny in the UI. Buggy's dashboard has engagements, findings and graph pages but nothing for recon progress, pending approvals or the evidence trail.

## Idea

One new page per engagement that renders the `status` snapshot and lets the operator answer approvals, reusing the existing approvals API route.

## Architecture

In `clients/web` (Next.js app router; read `clients/web/AGENTS.md` first and follow its conventions):
1. API route `src/app/api/engagements/[id]/status/route.ts`: GET returns the snapshot JSON. Implementation: read the same sources as `buggy-cli status` directly in TypeScript from the mounted roots (`CONTROL_PATH`, `AUDIT_PATH` env, already used by the existing approvals route — read that route first and reuse its path helpers): scope from `roe.json`, approvals join from the two JSONL files, `hunt-result.json`, `recon-report.md` presence. Recon live state: call the recon MCP server over HTTP if `BUGGY_MCP_RECON_URL` and `BUGGY_STACK_MCP_TOKEN` are set, else report `available: false`. Validate `id` with the same slug regex the other routes use; never read outside the roots.
2. Page `src/app/(dashboard)/engagements/[id]/run/page.tsx` (client component polling the route every 5 s): four panels — Scope (mode, in-scope, rate, sandbox network, approvals), Recon (stage stepper for the seven stages with the current one highlighted, record counts), Approvals (pending list with Allow / Deny buttons that call the existing approvals API; show method, URL, body preview), Findings (counts by status; table of exploit-verified). Link to it from the engagement detail page.
3. Use existing UI components (`components.json` is shadcn); no new dependencies.

## Files you own

- clients/web/src/app/api/engagements/[id]/status/** (new)
- clients/web/src/app/(dashboard)/engagements/[id]/run/** (new)
- clients/web/src/app/(dashboard)/engagements/[id]/page.tsx (add one link only)
- tests colocated per the web app's convention

## Out of scope

Python code. New npm dependencies. Changing the approvals API contract.

## Tests that must exist and pass

Run in `clients/web`: `npm ci`, `npm run lint`, `npx tsc --noEmit`, `npm run build` — all must pass. If the repo has a test runner configured (check `package.json`), add tests for the status route: fixture roots in a temp dir, asserts the approvals join, the slug validation (path traversal rejected), and the `available: false` path. If there is no runner, test the pure join/parse helpers with `node --test` on a `.ts`-free helper module and say so in your report.

## Done when

Lint, type-check and build pass; the route returns a correct snapshot for a fixture engagement.
