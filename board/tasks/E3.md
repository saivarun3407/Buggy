# E3 — Candidate queue: one deduplicated list of things to prove

Epic: **E05** · Lane: **E** · Depends on: E2

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

Shannon reconciles two streams (runtime analysis and source analysis) into one deduplicated exploitation queue before any exploit attempt. Buggy has three producers (pipeline scanner hits, probes, agents) and no single queue, so the same lead is chased repeatedly.

## Idea

Merge every lead into the findings store as `candidate`, dedupe by the stable finding id, and hand out the next most valuable one.

## Architecture

New `findings/candidates.py`:
- `from_pipeline(records: list[dict], engagement) -> list[dict]`: map recon `vulnerability` records to Finding-shaped candidates (`source="pipeline:nuclei"`, class via a fixed template-id/CWE map defined in this module — copy the minimal mapping logic, do not import `benchmark`), severity from the record; skip pure technology-detection templates (severity info and tag `tech`).
- `from_probe(result: dict, engagement, url, parameter="") -> dict | None`: a `probe_run` result with `vulnerable is True` becomes a candidate with `assertions` built from `evidence_capture_ids` and the probe's `details` (each probe documents which capture is baseline/control/proof; map them: proof capture -> `expect.status` = its recorded status; if details name an owner/attacker pair -> `same_as`). `vulnerable` False/None -> `None`.
- `from_ranked(candidates: list[dict], engagement) -> list[dict]`: the report's `rank_candidates` rows become low-priority leads (`source="pipeline:surface"`, status `candidate`, no assertions).
- `enqueue(service, items, actor)`: submit all; identical ids merge (union of assertions, highest severity, sources joined).
- `next_candidates(store, engagement, *, limit=5, claimed_by="") -> list[dict]`: order: has assertions first, then severity, then class priority (`access_control, auth_session, ssrf, business_logic, api, graphql, injection, xss, ...`), oldest first; supports a soft claim (`claimed_by`, `claimed_at`, 15-minute lease) so two agents do not take the same lead; `release`.

## Tests that must exist and pass

- three producers reporting the same IDOR -> one row with three sources and merged assertions.
- ordering rule (table-driven).
- claim lease: a claimed candidate is skipped for another agent until released or expired (inject the clock).
- technology-detection scanner hits are not enqueued (negative control).
- a probe result with `vulnerable=None` produces nothing.
