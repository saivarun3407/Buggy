# B5 — Project the recon store into the knowledge graph

Epic: **E07** · Lane: **B** · Depends on: B4

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

RedAmon's agent reasons over a Neo4j graph the recon pipeline writes (Domain -> Subdomain -> IP -> Port -> Service -> Endpoint -> Parameter -> Vulnerability). Buggy has the graph database and the recon data but they are not connected: agents get flat lists.

## Idea

A deterministic projection from recon records to typed nodes and edges, written to the existing KG by code, so agents can traverse relationships.

## Architecture

New module `pipeline/graph_export.py` with a pure core and a thin writer:
- `project(records: Iterable[dict], engagement) -> Graph(nodes: list[Node], edges: list[Edge])`.
  Node = `{key, label, props}`; Edge = `{src, type, dst, props}`. Keys are stable: `host:<name>`, `ip:<addr>`, `port:<host>:<n>/<proto>`, `svc:<base url>`, `url:<normalized url>`, `op:<METHOD> <url>`, `param:<METHOD> <url> <loc>:<name>`, `tech:<name>[@version]`, `issue:<template>:<matched_at>`, `spec:<url>`.
  Mapping (record type -> node label, edges): `subdomain` -> `Host`; `dns_record` A/AAAA -> `IP` + `(Host)-[:RESOLVES_TO]->(IP)`; `port` -> `Port` + `(Host)-[:HAS_PORT]->`; `http_service` -> `Service` + `(Host)-[:SERVES]->`; `technology` -> `Technology` + `(Service)-[:USES]->`; `url`/`endpoint` -> `Endpoint` + `(Service)-[:HAS_ENDPOINT]->`; `api_spec` -> `ApiSpec` + `(Service)-[:DESCRIBED_BY]->`; `api_operation` -> `Operation` + `(ApiSpec)-[:DECLARES]->` and `(Service)-[:HAS_ENDPOINT]->`; `parameter` -> `Parameter` + `(Operation|Endpoint)-[:TAKES]->`; `vulnerability` -> `KnownIssue` + `(Service)-[:HAS_ISSUE]->`; `graphql` -> `GraphQL` + `(Service)-[:HAS_ENDPOINT]->`. Every node carries `engagement`, `source_tool`, `record_id`, `last_seen`. Labels and relationship types must pass the KG store's validators (read `middleware/kg_internal/store.py` for `_safe_rel_type` and the label rules; if a label is not accepted by the store's schema, add it to a new migration file `V005__recon_projection.cypher` with a uniqueness constraint on `(key, engagement)`).
- `write(graph, store, *, engagement, created_by="pipeline") -> dict` uses the KG store's public upsert methods (read the store to find them); idempotent (same input twice = no new nodes).
- CLI entry `python -m buggy.pipeline.graph_export <engagement>` reads the recon store read-only and writes the projection; exits 0 with a message when the KG is not configured.
The projection never deletes agent-created nodes.

## Out of scope

Calling the projection from the worker (integrator decides where). Agent prompts.

## Tests that must exist and pass

- pure projection: a fixture of ~20 records -> exact expected node keys/labels and edge triples.
- idempotence against a fake store that counts upserts by key.
- a record on an out-of-scope host never produces a node (the projection only accepts records already in the store, but assert the function ignores records whose `status` is `gone`).
- every label / relationship type passes the store's validators (call them).
- if a migration is added: `ensure_schema` against the fake store used in `tests/unit/hardening/test_kg_runtime.py` applies it.

## Done when

New tests green; KG and pipeline suites still green.
