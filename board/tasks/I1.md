# I1 — Integration: expose the new capabilities to agents through the stack's MCP servers

Epic: **INT** · Lane: **I** · Depends on: D5, E6, F6, B6, C5

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

Everything above is a library until an agent can call it and an operator can see it.

## Idea

Register the reserved tool names on the capture server, add thin agent-side wrappers that bind the engagement, and update the hunt kickoff so agents use the queue, verifier, identities, memory and board.

## Architecture

Done by the orchestrator, serially, after the lanes finish:
- `capture/mcp_server.py`: construct `FindingService`, `SessionManager`, `LessonStore`, `Board` over `/data/capture`; register `finding_submit, finding_get, findings_list, finding_verify, finding_grade, candidates_next, report_build, evidence_export, identities_list, authz_matrix_run, memory_search, memory_save, fact_add, facts_list, intent_open, intent_claim, intent_conclude, hints_list, hint_add`; `http_send` gains `identity`; successful probes are enqueued as candidates automatically.
- `tools/stack_mcp.py`: wrappers for each (engagement bound from the run); role mapping.
- `pipeline/mcp_server.py`: `recon_coverage`; worker calls the graph projection after a run when the KG is configured.
- `cli/hunt.py`: after recon, enqueue pipeline candidates; kickoff tells agents to work the queue, call `finding_verify`, read lessons, use the board; at the end build the report (Markdown, HTML, JSON, SARIF) into the control dir and write `hunt-result.json`.
- `agents/middleware_slots.py`: add the loop guard; notifier hooks at approval/recon/finding/failure points.
