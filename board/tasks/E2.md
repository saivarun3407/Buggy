# E2 — Grade: submit, hold or discard, with stated reasons

Epic: **E05** · Lane: **E** · Depends on: E1

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

Hacker Bob adds a GRADE stage after VERIFY: each surviving finding is ready to submit, held, or discarded. Its criteria are not published; ours are, as code.

## Idea

A deterministic grader that turns a verified finding plus program rules into a decision the operator can trust and audit.

## Architecture

New `findings/grade.py`: `grade(finding, *, program: dict | None, scope, known_issues: list[dict], prior: list[Finding]) -> Grade(decision, reasons: list[str], blocking: list[str])`.
Rules, evaluated in this order; every rule that fires adds a reason:
 1. `status != exploit_verified` -> `hold` ("not exploit-verified: <status>"); `discarded` -> `discard`.
 2. endpoint host not allowed by `scope.allows` -> `discard` ("out of scope now").
 3. class or title matches a program `excluded_classes` entry (case-insensitive substring, min length 4) or a baseline banned technique (`denial_of_service`, `social_engineering`, `physical`) -> `discard`.
 4. remediation shorter than 30 chars or a placeholder -> `hold`.
 5. duplicate: another finding in `prior` with the same id and grade `submit` already -> `discard` ("duplicate of <id>"); a `known_issues` entry (pipeline vulnerability record) with the same class and endpoint -> `hold` ("already reported by scanner template <id>: confirm it is not a known/accepted issue").
 6. severity above the program's `severity_caps` for that host -> keep decision, add reason "severity capped to <cap>" and return `capped_severity`.
 7. severity `info`, or class `misconfiguration` with severity `low` -> `hold` ("low signal: most programs do not pay for this").
 8. otherwise -> `submit`.
`blocking` lists what must change for a `hold` to become `submit`.
`FindingService.grade(engagement, id, ...)` stores the grade and an event.

## Out of scope

Platform API calls, duplicate lookups against HackerOne (task F5 supplies local data only).

## Tests that must exist and pass

Table-driven: one test per rule plus combinations: verified high IDOR in scope with remediation -> submit; unverified -> hold; excluded class -> discard with the program's wording in the reason; out-of-scope host -> discard; duplicate -> discard; scanner-known -> hold; severity cap applied; info -> hold. Assert reasons are complete sentences naming the rule. A finding that should submit must not be held by an unrelated known issue on a different endpoint (negative control).
