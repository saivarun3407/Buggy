# E4 — Report: Markdown, self-contained HTML and JSON from one finding schema

Epic: **E11** · Lane: **E** · Depends on: E3

Read `board/AGENT_RULES.md` and `board/CONTRACTS.md` first.

## Why (who does this well, and what Buggy lacks)

Shannon ships PDF + Markdown + JSON with evidence and only validated findings; Xalgorix a branded PDF with CVSS, PoC and remediation. Buggy's recon report covers scanner results only; verified findings have no report.

## Idea

One renderer over the findings store: verified findings first, with reproduction and remediation; everything unverified in clearly labelled appendices.

## Architecture

New `findings/report.py` (pure functions, stdlib only):
- `build(engagement, findings: list[dict], *, recon_summary: dict | None, scope: list[str], captures: Callable[[str], dict | None], generated_at) -> Report` (a dict): `summary` (counts by severity of exploit_verified only; counts of inconclusive / candidates / discarded; `complete: bool` passed in), `findings` (exploit_verified, sorted by severity then id), `unverified` (inconclusive + source_verified, labelled), `leads` (candidates), `scope`, `method` (one paragraph: what verified means here).
  Each finding block: id, title, severity, CWE, class, endpoint, method, parameter, description, **reproduction** (numbered steps generated from assertions: for each, method + URL + identity name + the expectation in words, and the `capture_id`), **proof** (status line and first 600 chars of the response of the verifier's replay capture, fetched through `captures(id)`; redacted headers stay redacted), remediation, grade + reasons.
- `to_markdown(report) -> str`, `to_json(report) -> str` (stable key order), `to_html(report) -> str`: one self-contained file, inline CSS, light/dark via `prefers-color-scheme`, no scripts, every dynamic string escaped with `html.escape` (finding text is attacker-influenced: a title containing `<script>` must render as text).
- No PDF here (the integrator can print the HTML through the browser service).
- Wording rule: the words "vulnerability" / "finding" in headings refer only to exploit_verified items.

## Files you own

- packages/buggy/buggy/findings/report.py (new)
- packages/buggy/tests/unit/findings/test_report.py (new)

## Out of scope

PDF. Platform-specific templates (HackerOne/Bugcrowd renderers already exist under `tools/reporting`). Writing files.

## Tests that must exist and pass

- a fixture with 2 verified, 1 inconclusive, 3 leads, 1 discarded -> the three formats contain the right sections and counts; discarded items appear only as a count.
- HTML escaping: titles/descriptions/response excerpts with `<script>`, quotes and `&` are escaped in HTML and unchanged in JSON.
- reproduction steps are generated from assertions (assert exact lines for an IDOR and for a single-request finding).
- redaction: a capture with an Authorization header never leaks it in any format.
- empty findings -> a valid report that says nothing was verified (and still lists leads).
- JSON round-trips and is byte-stable for the same input.
